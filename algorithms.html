Prioritizing Inventory Restocking

markmdev | CS-499 | September 28, 2026

Artifact and purpose

Inventory Tracker began as my Java Android application for CS-360 Project Three in August 2026. Its SQLite database stores item quantities and low-stock thresholds. The original low-stock query returns eligible items ordered by raw quantity. That order cannot distinguish two units against a threshold of three from three units against a threshold of thirty. I selected this artifact because that limitation creates a useful algorithm problem inside an application that already works.

This milestone implements the restock shortlist proposed in Module One. It builds on the stock-adjustment workflow submitted in Module Three. The accompanying archive preserves the original CS-360 source and includes the cumulative enhanced source, tests, benchmark, and real emulator evidence. The main inventory screen still shows all items; the shortlist is a separate view.

Ranking and selection

An item is eligible when its quantity is at or below its threshold. Stockouts come first. Remaining candidates are ordered by their quantity-to-threshold ratio, then by case-sensitive SKU and item ID. Thus, three units against a threshold of thirty precede two units against a threshold of three. This is a stated prioritization rule, not a demand forecast. A zero threshold qualifies only at zero quantity and is handled as a stockout before any ratio comparison.

RestockSelector compares ratios through long integer cross-products. The quantity and threshold are nonnegative Java int values, so their products fit in a signed long. This avoids rounding near equal ratios. The repository supplies unique IDs; SKU and ID make equal-priority results deterministic. Negative limits are rejected, zero requests return an empty list, and a limit larger than the eligible count returns every candidate without allocating an array of that requested size.

The priority queue retains at most k candidates. Its comparator is reversed so that the least urgent retained candidate is at the root. A better candidate replaces that root; worse candidates are discarded. Finally, the retained candidates are sorted into display order. Oracle (n.d.) documents logarithmic insertion and removal for PriorityQueue, supporting the selection analysis below. The queue’s internal iteration order is not used as the output order (OpenAI, 2026).

For n loaded items, m eligible items, and h = min(k,m), selection takes O(n + m log(h+1)) time and O(h) auxiliary space for k > 0, followed by O(h log(h+1)) output ordering. The full-sort reference takes O(n + m log(m+1)) time and O(m) auxiliary space. Both approaches receive the existing O(n) repository list. These are selection costs after loading: the SQLite query already orders records by name, and database access and screen rendering are outside this comparison.

Evaluation in the application

The shortlist runs on the existing background executor and survives screen recreation with its requested limit. Selecting a row opens the established adjustment preview. Returning after confirmation reloads the shortlist, so the displayed quantities and ranking reflect the database. A review caught a case where a blank limit could prevent that reload and leave old results visible. The validation path now clears the old list, and an emulator regression reproduces the sequence.

Six new unit tests cover stockouts, relative coverage, equal ratios, SKU/ID ties, empty inputs, zero and oversized limits, invalid values, and near-maximum integer products. Randomized comparisons use a separately written BigInteger rational comparator rather than trusting the production comparator as its own oracle. Across 100 generated inventories and six requested limits per inventory, the selected IDs match that reference and contain no duplicates. Together with the prior three unit tests, all nine pass. All twelve emulator tests pass, including the new shortlist workflow and the previous account, adjustment, and database-failure regressions. Android lint reports no errors; existing warnings remain.

What the measurements show

The benchmark uses generated inventories on the local macOS ARM64 host with JDK 21. Each case has ten warmup runs and twenty-one measured runs per algorithm; execution order alternates, and the table reports medians in milliseconds. Both algorithms returned identical IDs and order for each benchmark case before timing. These measurements cover selection in memory, not device or end-to-end application performance.

The heap fits a short restock list: it avoids sorting thousands of candidates to show five. It is not universally faster. At 100,000 requested results, full sorting wins in this run, and the absolute difference for a 100-item inventory is tiny. I retained the simpler full-sort implementation as a comparison instead of claiming that a heap should replace every sort. The archive includes all nine measured cases and the runnable benchmark.

Learning and outcome alignment

The main lesson was that ordering and selection are separate decisions. Reversing the comparator for the heap is easy to get wrong, while floating-point ratios can hide an ordering error. Explicit examples, independent arithmetic, and randomized tests made those decisions checkable. The UI refresh issue also showed that a correct selector is not enough if the application presents an old result after stock changes.

The completed enhancement supports the planned outcomes 3 and 4 through algorithm design, evaluated tradeoffs, and integration into a useful Android feature. This narrative, benchmark explanation, and preserved code-review plan support outcome 2. No outcome-coverage plan change is needed. Security remains supported by the earlier validation and adjustment work; this milestone does not claim new authorization or audit-history capabilities. The database is still version 1, and durable movement history remains the next enhancement. Instructor feedback on this milestone will guide the final portfolio revision.
