Inventory Tracker · Enhancement narrative

Keeping Stock Changes Explainable

markmdev | CS-499 | October 4, 2026

Artifact and purpose

Inventory Tracker is the Java Android application I created for CS-360 Project Three in August 2026. The original app stored the current quantity but could not explain how it got there. My first capstone enhancement added an adjustment preview and reason, but the reason disappeared after the operation. This database enhancement closes that gap: a confirmed stock change and its explanation now persist together.

I selected this artifact because data integrity matters to the same operation at every layer. A useful preview cannot compensate for a database that saves half of an adjustment. This milestone follows my Module One plan and Module Two code review. The archive preserves the original CS-360 source and includes the cumulative enhanced app, with the earlier adjustment workflow and restock shortlist intact.

Preserving data while changing the schema

The database helper now opens schema version 2. Its upgrade creates stock_movements and an item-history index without dropping or rebuilding the existing users and inventory tables. Existing accounts still authenticate, and item IDs, quantities, and thresholds remain unchanged. The migration starts history empty; making up movements for existing quantities would imply knowledge the original app never recorded.

Each movement stores the item reference, SKU and name snapshots, old quantity, signed change, new quantity, reason, and UTC time in epoch milliseconds. The reference is nullable with ON DELETE SET NULL, and foreign keys are enabled when the connection is configured. Deleting an item therefore retains its movement rows and their identifying snapshots. SQLite documents both the need to enable foreign-key enforcement and the SET NULL behavior (SQLite, n.d.-b). The screen shows history for existing items; retained records for deleted items remain in SQLite. This is local traceability, without employee attribution or protection against someone directly modifying the database.

One transaction for both writes

Confirmation starts a transaction and reloads the item. A missing item or a quantity different from the preview produces an explicit result without a new movement. The operation validates the signed change and reason again, updates exactly one matching item, then inserts the movement using the current item snapshot. It commits only after both writes succeed. SQLite transactions provide the boundary for keeping those writes together (SQLite, n.d.-c).

The new table also checks integer quantity bounds, a nonzero change, a nonempty reason, and the equation old quantity + change = new quantity. I included storage-type checks because an INTEGER column declaration alone does not reject fractional values. Inserts use ContentValues and history queries bind the item ID rather than constructing SQL from user text. These decisions and their failure tests were developed with Codex assistance (OpenAI, 2026).

The existing background worker loads the history screen. Entries show before and after quantities, the signed change, reason, and UTC timestamp. Newest entries appear first, with movement ID breaking equal-time ties. An index on item ID, timestamp, and movement ID supports that access pattern. In the emulator, EXPLAIN QUERY PLAN reports an indexed search and no temporary sorting tree. Removing the index from a disposable test database produces a table scan and a temporary sorting tree. That is evidence about the query strategy, not a measured speedup (SQLite, n.d.-a).

Verification and what I learned

The most useful test deliberately rejects the movement insert after the quantity update. Starting from ten units, a +5 adjustment fails and leaves ten units with no movement. Removing the test trigger lets the same operation save fifteen units and exactly one record. Testing only successful inserts would have missed the problem this transaction is supposed to prevent.

A separate migration test starts with a populated version-1 database. It verifies the existing login, rejects a wrong password, checks the preserved item values, and confirms that no history was invented. Other database tests cover persistence after reopening, stale and missing items, retained deletion snapshots, invalid and fractional values, filtering, and tied timestamps. The interface test opens empty history, confirms a 10-to-7 adjustment, then reads that movement after screen recreation. Earlier cancellation and repeated-confirmation checks now inspect movement counts as well as quantities.

All nine unit tests and twenty emulator tests pass. The emulator run includes the earlier login, item, notification-screen, adjustment, and restock regressions. Android lint reports no errors; warnings remain. The archive contains the actual reports, database evidence, and a screenshot of the working history screen.

The challenge was deciding what history should promise. A foreign key alone would lose the useful identity of a deleted item; a snapshot alone would lose the relationship used for the normal history query. Combining them makes the deletion policy explicit. I also had to distinguish successful UI feedback from a committed database operation. The rollback test made that distinction concrete.
