Professional Self Assessment

markmdev | CS-499 | October 18, 2026

The kind of engineer I want to be

I started programming because I wanted to make games. I still enjoy getting a feature to work, but the Computer Science program has changed what I consider finished. A working screen is only part of the result. I also need to explain the design, understand its costs, and show what happens when input is wrong or an operation fails. That is the direction of this portfolio: taking a small inventory application and making its behavior easier to review and trust.

I work as a software engineer at a startup, primarily with JavaScript, TypeScript, and Python. My interests are application APIs and AI agents, with architecture and technical leadership as longer-term goals. The degree has helped connect that practical background to more deliberate analysis. I am more employable when I can defend a choice with evidence and explain its limits, rather than only demonstrate the successful path. Preparing this portfolio made me apply that standard to my own work.

Making decisions other people can review

My coursework has given me practice explaining technical choices to people approaching the same problem differently. In a CS-300 discussion about inventory data structures, I responded to a proposed vector by asking which operation mattered most: looking up one product by serial number or displaying an ordered list. That changed the comparison from a preference for a container to a question about the user's work. A hash table helps frequent lookups, while ordered output introduces another cost. This is the kind of discussion I want to contribute in a team: establish the requirement, make the tradeoff visible, and leave room for a different answer when the requirement changes.

These were individual assignments and peer discussions, not a shared production project. I do not present them as proof that I led a development team. They did teach me useful collaboration habits. A reviewer needs enough context to disagree productively. For this capstone, I preserved the baseline, separated the enhancements into reviewable milestones, documented setup and failure behavior, and recorded a code review before implementation. A teammate can compare the plan with the result instead of reconstructing the intent from a finished application.

Communication also changes with the audience. My CS-340 animal-shelter dashboard connected MongoDB queries to rescue-category filters, a data table, a map, and a breed chart. A user needs to understand what a filter changes; a developer needs to understand the query and callbacks behind it. That project made the connection between database structure and the information a stakeholder can actually use much clearer to me. In this portfolio, short before-and-after explanations introduce each feature, while source files, measurements, and narratives provide the technical detail.

Applying theory to working software

CS-300 gave me a concrete reason to compare data structures before implementing one. The course-advising project considered vectors, hash tables, and binary search trees, then used a hash table for course lookup with separate sorted output. The important lesson was to account for the whole workflow. Fast lookup does not make file validation or sorting free. I carried that distinction into the capstone benchmark, which measures selection after data is loaded and does not claim to measure database or screen performance.

Software engineering and databases came together in CS-340, where a reusable Python CRUD module separated database access from the dashboard. Maintaining that boundary makes a change easier to reason about. The capstone extends the same idea in Android: the Activity renders the interface, the ViewModel owns operation state, and the database helper owns persistence. The question is not just where to put a method. It is which layer can decide whether a requested change is still valid and whether it actually committed.

CS-305 helped me approach security as an examination of concrete failure paths. The Artemis Financial vulnerability assessment considered code-level weaknesses as well as dependencies, and the later work used HTTPS and checksum verification. Those exercises made me more careful about what a security claim proves. A checksum does not establish authorization, and a scanner does not decide whether every reported issue is exploitable. In the inventory app, parameterized access, validated quantities, stale-preview rejection, and rollback tests protect specific operations. The app still has shared local inventory, no employee roles, and no tamper-proof audit log. Naming those boundaries is part of the security work.

How the portfolio fits together

The technical artifact is Inventory Tracker, a Java Android app created for CS-360 in August 2026. I chose one application so that each enhancement had to work with the others. The original source and the cumulative enhanced version are available together. The code-review video explains the original behavior and planned changes; the three narratives explain what I implemented and learned.

The software-design enhancement replaces immediate quantity changes with a reason, preview, and confirmation. It handles cancellation, repeated confirmation, obsolete quantities, and screen recreation. The algorithms enhancement adds a bounded-heap restock shortlist with exact ratio comparisons and an independently checked full-sort alternative. The database enhancement stores stock changes and their explanations in one transaction, preserves existing records during migration, and retains movement snapshots when an item is deleted.

The final milestone verification records nine unit tests and twenty Android tests. A deliberately rejected history insert leaves both stock and history unchanged; the ranking comparison also shows where full sorting is faster than the heap. Those results matter more to me than claiming one solution always wins. The instructor's feedback on the code review and all three enhancements requested no corrections, so I retained their technical scope and used the final assembly to make the relationship between design, algorithms, and persistence easier to follow.

I want to keep building systems whose behavior can be explained at that level. My next growth area is applying these habits in larger shared systems, where authorization, concurrent users, and operational recovery add problems this local app does not solve. This portfolio shows the foundation I can bring: practical implementation, explicit tradeoffs, and evidence that another developer can inspect.
