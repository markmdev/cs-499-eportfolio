Inventory Tracker · Enhancement narrative

Software Design and Engineering Enhancement

markmdev | CS-499 | September 20, 2026

Artifact and purpose

Inventory Tracker is the Java Android application I completed for CS-360 Project Three in August 2026. It provides account creation, login, a shared SQLite inventory, and optional low-stock SMS alerts. I chose it because the original quantity buttons expose a small but meaningful design problem: a tap writes immediately, without a reason or a chance to review the result. The original source is preserved alongside the enhanced project in the accompanying ZIP.

The enhancement replaces those buttons with an adjustment workflow. A user enters a signed quantity change and a reason, reviews the current and proposed quantities, then confirms or cancels. For example, a shipment of five units changes a quantity of 10 to a preview of 15. Cancel leaves 10 in storage. Confirmation succeeds only if the stored quantity still matches the preview. If another adjustment changes it to 11 first, the app rejects the old preview and requires a new review showing 16.

Design and demonstrated skills

MainActivity renders the interface. InventoryViewModel owns the current screen and operation state, schedules work on a single background executor, and posts results to the main thread. InventoryDatabaseHelper remains the persistence owner and now returns explicit applied, stale, or missing results. StockAdjustment is an immutable preview that validates a nonzero delta, a nonblank reason, and a resulting quantity within the Java integer range. Addition uses a long value before conversion, so overflow cannot silently turn a large stock count negative.

The operation has editing, loading, preview, saving, success, and error states. Confirmation enters saving before scheduling the write, which blocks repeated commands. The persistence method checks the expected quantity in a transaction and requires one updated row. Database errors do not produce a success message; the user must preview current stock again. Account hashing, inventory reads, item creation/deletion, and the low-stock query also run off the UI thread.

The important lifecycle decision was to retain the operation rather than ask a recreated Activity to repeat its last action. Android’s ViewModel guidance describes retaining state and asynchronous work across configuration changes (Google, 2026). The new Activity observes the same operation after rotation. Commands are not serialized for process restoration: a new process starts at login, then reloads stock and requires a new adjustment. This avoids treating restored screen data as permission to write.

Results and learning

Three local test methods cover signed changes, blank reasons, zero changes, negative results, and integer boundaries. Eleven Android tests exercise the real Activity and SQLite database: positive and negative adjustments, cancellation, invalid input, stale and missing items, failure recovery, editing/preview recreation, and recreation while saving. The saving test holds a separate database transaction open, requests confirmation twice, recreates the Activity, releases the transaction, and verifies one change from 10 to 15. A temporary SQLite trigger rejects a test write to verify that the error remains visible and a later fresh preview can recover. Regression checks exercise account creation, login, item creation/deletion, and the notification screen. Additional checks verify that recoverable errors preserve form entries and closing an Activity during a blocked write does not restart its disposed worker. I did not send an SMS during these regression checks.

The main lesson was that disabling a button and retaining a screen are not enough by themselves. The operation must reject repeated confirmation, and persistence must reject an obsolete quantity. I also replaced a legacy Back override after Android lint identified that it would not handle newer back gestures. The build, local tests, emulator tests, and lint checks passed after that correction. The app still has the original shared-inventory model; this change adds no employee roles or cloud synchronization.
